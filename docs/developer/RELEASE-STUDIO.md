# Release Studio

Release Studio turns an existing signed MOBAflow version tag into a reviewable draft GitHub Release. It validates the tag, generates release notes from the commit history, builds and tests the Windows application, packages the self-contained x64 output, creates an SPDX SBOM of the shipped package, signs GitHub build provenance for the ZIP and the SBOM, creates checksums, and attaches the artifacts to a draft release.

It does not create tags and it never publishes a release automatically.

## Prerequisites

- The release commit is on the remote repository.
- The commit titles since the previous version tag follow Conventional Commits (`feat:`, `fix:`, `refactor:` and so on). Release Studio turns them into the draft notes with git-cliff and the `cliff.toml` of the default branch. A stable tag covers all commits since the previous stable tag, including those already listed for its release candidates; `CHANGELOG.md` is not used for the notes.
- The plain Semantic Version tag exists without a `v` prefix, for example `0.2.1`.
- The tag is annotated and signed with a key that GitHub recognizes as verified.

Create and push the tag from a trusted maintainer workstation. Replace `origin` with the name of your GitHub remote if it differs (`git remote -v` lists it):

```powershell
git switch main
git pull --ff-only
git tag -s 0.2.1 -m "Release 0.2.1"
git push origin 0.2.1
```

## Create a release candidate

1. Open **Actions > Release Studio** in GitHub.
2. Select **Run workflow**.
3. Enter the existing tag.
4. Select whether the draft represents a prerelease.
5. Start the workflow and review every completed step.
6. Download and test the workflow artifact when an additional local check is useful.
7. Open the generated draft under **Releases**.
8. Edit the generated notes into user-facing wording, then review the attached ZIP, SBOM, provenance bundle and `SHA256SUMS.txt`. Preview the notes locally with `git cliff --unreleased --strip header` before tagging.
9. Publish the draft only after the release candidate has passed manual application and hardware checks.

## Release checklist

- [ ] The selected commit is the intended release commit.
- [ ] The signed tag is visible as verified on GitHub.
- [ ] Automated build and tests pass.
- [ ] MOBAflow starts on a supported Windows system.
- [ ] MOBApi starts with MOBAflow and remains restricted to the private network.
- [ ] Z21 connection, emergency stop, locomotive control, and feedback monitoring are manually checked.
- [ ] Existing project files open successfully.
- [ ] Release notes describe user-visible changes and breaking changes.
- [ ] The ZIP and SBOM checksums match `SHA256SUMS.txt`.
- [ ] `gh attestation verify` succeeds for the ZIP and the SBOM (see below).
- [ ] The SBOM coverage report (job summary and workflow artifact) lists no unexplained gap; every entry under `gaps` has a known origin.
- [ ] The draft release contains no secrets, logs, local settings, or development files.

## SBOM and build provenance

Each run produces, next to the ZIP and without duplicating it:

- `MOBAflow-<tag>-win-x64.spdx.json`: an SPDX 2.3 SBOM generated by `scripts/New-ReleaseSbom.ps1` from the exact validated publish directory. It lists every shipped file (MOBAflow, bundled MOBApi, runtime and native files) with its SHA-256, the NuGet packages from the restore assets, and the ZIP digest, tag, commit and run URL. `scripts/Test-ReleaseSbom.ps1` re-checks it against the finished ZIP before anything is attested.
- `MOBAflow-<tag>-win-x64.provenance.sigstore.json`: the GitHub build provenance attestation bundle for the ZIP and the SBOM, signed through OIDC (`id-token: write`, `attestations: write` on the job only; no signing secret).
- `MOBAflow-<tag>-win-x64.sbom-coverage.json` (workflow artifact and job summary): shipped files per category and explicit `gaps`. Files that match neither a NuGet package, an own project nor a known runtime name are reported as `native-or-unclassified-binary` or `other-unclassified`; the release maintainer identifies them before publishing. File-to-package mapping is by file name only, and licenses are `NOASSERTION`.

`SHA256SUMS.txt` lists the ZIP and the SBOM. Verify a downloaded release (replace the tag):

```powershell
gh attestation verify MOBAflow-0.2.1-win-x64.zip --repo ahuelsmann/MOBAflow
gh attestation verify MOBAflow-0.2.1-win-x64.spdx.json --repo ahuelsmann/MOBAflow
./scripts/Test-ReleaseSbom.ps1 -Sbom MOBAflow-0.2.1-win-x64.spdx.json -Archive MOBAflow-0.2.1-win-x64.zip -Tag 0.2.1 -Commit <tag commit sha>
```

A modified ZIP or SBOM fails both checks. Provenance proves where and how the files were built; it does not prove product readiness or the absence of vulnerabilities (manual release acceptance stays in #144). The attestation records the workflow run on the default branch, while the SBOM binds the tag commit that was built. User wiki: no change is needed before the first tester download; add the verification commands there when #144 publishes a release.

## Safe re-runs

Running Release Studio again for the same tag updates the assets of an existing draft and keeps its notes, including your edits; the freshly generated notes are only in the job summary and the workflow artifact. It refuses to modify a published release. Delete an unwanted draft manually only after confirming that no one is reviewing it.

## Troubleshooting

### The tag is lightweight

Delete the incorrect remote tag only when it has not been used for a release, then recreate it as a signed annotated tag from a trusted workstation.

### GitHub cannot verify the signature

Confirm that the signing key is associated with the maintainer's GitHub account and that the tag displays as verified in the repository. Release Studio intentionally rejects unknown or unverifiable signatures.

### A published release already exists

Published releases are immutable to this workflow. Create a new patch version when release contents need to change.
